# macOS Prompts 界面与功能改进方案

日期：2026-10-28。状态：待评审，尚未修改 App 实现。

本方案基于当前 SwiftUI/Go 代码，以及使用隔离资料库实际查看的 Prompts 列表、详情和编辑弹窗。测试内容包含中文长描述、多标签、Markdown 标题、列表和代码块，不涉及个人资料库。

已确认本次优先改善查找、阅读、复制和编辑。建议先把 Prompts 做成一个顺手的「查找 → 阅读 → 复制 → 编辑」工具，再扩展收藏、全文搜索或变量工作流。第一阶段保留三栏结构、当前标签分组和既有数据格式。

## 1. 已确认的问题

| 问题 | 现状与依据 | 对使用的影响 |
| --- | --- | --- |
| 同一栏缺少统一对齐线 | 列表标题左边距 20，搜索外边距 16，行内容另外使用 10；详情使用左 42、右 60 的外边距，正文卡片又增加左 20、右 56 | 列表、标题、正文起点不一致；正文可用宽度偏小 |
| 主操作看不出重点 | 快速查看、复制、导出、编辑、删除全部是同权重图标；复制使用回形针、导出使用气泡、编辑使用标签图标 | 需要逐个悬停才能理解；删除占据高频操作位置 |
| 阅读区存在重复层级 | 名称、描述、来源徽章、标签徽章、「内容」标题、卡片、卡片复制按钮逐层叠加；顶部还提供另一处复制 | 对简单文本而言装饰和容器偏多，阅读路径被拉长 |
| 右键菜单与当前条目无关 | 条目右键只提供新建、导入和标签管理 | 无法直接复制、编辑或创建当前 Prompt 的副本 |
| 编辑器存在真实的规则冲突 | 名称输入框可修改，但 Go `UpdatePrompt` 明确禁止修改已有名称 | 用户编辑后到保存时才收到拒绝，界面给了错误预期 |
| 编辑缺少校验解释 | 名称、描述和正文为空时保存禁用；名称规则、未声明变量等主要依赖保存时才校验 | 无法就地理解该改哪里 |
| 编辑布局刚性较强 | 弹窗固定 920 × 640，信息栏固定 280；正文标题与 TextEditor 使用不同 inset | 视觉起点不齐，窗口变窄或文字变长时不够灵活 |
| Markdown 支持不完整 | 共享渲染器只显式识别标题、代码块和段落，其他行进入 inline-only 解析；实测列表仍显示原始连字符 | 「预览」与用户对 Markdown 排版的预期有差距 |
| 新建后缺少定位 | `savePrompt` 丢弃创建返回值；刷新时保留旧选择，或选择列表第一项 | 资料多时可能找不到刚创建的内容 |
| 已有能力缺少入口 | Core 已提供 Prompt 历史和渲染，当前 Prompt 页面未接入历史；变量编辑/渲染组件存在，但不在现有流程中 | 有些增强无需重写底层；但不应默认恢复此前主动隐藏的变量流程 |

代码定位：

- [Prompts 页面与编辑器](../macos/SKMApp/Sources/Features/PromptsViews.swift)：列表菜单、详情按钮、正文内边距、名称输入框、保存规则。
- [列表摘要行](../macos/SKMApp/Sources/Features/PromptSummaryRow.swift)：行内信息与动态高度。
- [共享尺寸与阅读布局](../macos/SKMApp/Sources/App/DesignSystem.swift)：`CollectionHeader`、`DetailToolbar`、`libraryReadingLayout`。
- [AppModel](../macos/SKMApp/Sources/App/AppModel.swift)：`savePrompt`、`importPrompt`、`reload`、历史与渲染接口。
- [Markdown 渲染](../macos/SKMApp/Sources/Features/SkillsViews.swift)：`MarkdownBodyView`。

## 2. 推荐的整体方向

采用「阅读优先」作为默认方案：保持原生三栏，把主操作和内容排版整理清楚。另提供「紧凑浏览」作为评审备选：同样保留三栏和标签分组，减少每行信息高度，适合 Prompt 数量较多的情况。两者选定一个默认即可，不必为了方案对比给产品增加一套设置。

### 列表栏

- 标题、搜索框边缘、分组行的内容区使用统一的 20 pt 水平边距；折叠箭头作为单独的缩进槽处理。列表项名称与分组文字对齐，数量统一右对齐。
- 保留「全部默认展开、标签默认折叠」。同一 Prompt 可出现在多个标签组中，选中身份仍是同一个 ID。
- 名称一行、描述最多一至两行、标签一行；同一密度下预留一致的摘要空间，不让短描述和长描述随意改变视觉节奏。
- 长名称使用尾部截断并可悬停查看完整名称。当前中间截断更适合路径，不利于扫描文本名称。
- 行右键菜单改为：复制正文、编辑、创建副本、导出、删除。新建、导入和标签管理留在列表标题区或空白区菜单。
- 搜索时保留可见的结果数；无结果时提供清除搜索。若当前选择被过滤，详情切换为搜索结果或说明状态，不继续无提示地展示一个看不见的选择。
- 创建、导入或复制成功后，选择并滚动定位到返回的 Prompt；必要时清除阻挡定位的搜索，给出明确反馈。

### 详情栏

```text
┌─────────────────────────────────────────────────────────┐
│ 复制正文                  编辑             更多 ⋯       │
├─────────────────────────────────────────────────────────┤
│                                                         │
│ code-review                                             │
│ 检查代码的可读性、边界条件和潜在问题。                    │
│ 本地  ·  review  ·  开发                                 │
│                                                         │
│ 预览  |  源文                                           │
│ ─────────────────────────────────────────────────────── │
│ 你是一位资深工程师。                                    │
│                                                         │
│ 审查重点                                                │
│ • 正确性与边界条件                                      │
│ • 可维护性与命名                                        │
│                                                         │
└─────────────────────────────────────────────────────────┘
```

- 名称、描述、元数据、内容切换条和正文共用一条左对齐线。建议详情水平边距 28～32 pt，正文阅读宽度上限约 760～840 pt；这是本项目的起始设计值，需要通过窄窗、中英文和长文本实测调整，并非平台硬性标准。
- 去掉整段正文外的大卡片和重复「内容」标题；代码块、引用等有语义的内容继续保留各自样式。
- 高频操作保留「复制正文」「编辑」。两者都有可见文字和正确图标；低频操作集中到更多菜单，不把删除常驻在主要工具栏中。
- 更多菜单：创建副本、导出 Markdown、历史版本、快速查看、删除。删除单独分组，继续确认。
- 复制始终复制保存的 Markdown 正文，不含文件元数据，也不因当前显示「预览」或「源文」而改变。保留正文的空格、换行与占位符。
- 复制成功直接在原按钮上显示「已复制」，随后恢复；不要同时弹全局状态气泡和局部反馈。
- 来源改为低强调文字，标签保持轻量样式。通用「可用」绿勾当前来自默认健康值，不表达独立的 Prompt 检查结果，建议移出此处。
- 详情明确区分加载中、读取失败、无选择。读取失败提供当前页面内的重试入口，避免只剩一个持续加载提示。

### 新建与编辑

```text
┌─────────────────────────────────────────────────────────┐
│ 编辑 Prompt                                             │
├───────────────────┬─────────────────────────────────────┤
│ 名称              │ 正文               编辑 | 预览      │
│ code-review       │                                     │
│ 创建后固定        │ 你是一位资深工程师。                │
│                   │                                     │
│ 描述 *            │ ## 审查重点                         │
│ …                 │                                     │
│                   │ - 正确性与边界条件                  │
│ 标签              │ - 可维护性与命名                    │
│ review  开发      │                                     │
├───────────────────┴─────────────────────────────────────┤
│ 未保存的更改                         取消       保存    │
└─────────────────────────────────────────────────────────┘
```

- 新建时名称可填写并校验格式；编辑时名称只读，说明创建后固定，并提供「创建副本」入口。第一阶段不改底层身份规则。
- 名称、描述、正文的必填规则在填写时可见；保持现有 Go 校验，不悄悄把描述改为可选。
- 左侧信息栏保持紧凑，右侧正文占主要空间；正文标题和编辑内容的首字符对齐。应明确处理原生 TextEditor 的实际文本 inset，而非继续叠加补偿 padding。
- 默认专注编辑，使用「编辑 / 预览」切换；不强制同时展示两份正文。编辑器和详情使用同一套 Markdown 渲染规则。
- 取消、保存始终固定在底部，保存支持 `⌘S`；已有未保存提醒和并发冲突处理继续保留。
- 没有改动时禁用编辑保存；失败时保留草稿，并在相关字段旁说明问题。并发修改仍提供使用磁盘版本、创建副本、基于最新版本再保存三条明确路径。
- 内容按可用空间布局，避免固定 920 × 640：较窄时将信息区收为上方可折叠区域，保证正文仍可编辑；先验证当前最小主窗口 980 × 640。

## 3. 功能优先级

| 阶段 | 范围 | 目的与实现边界 |
| --- | --- | --- |
| P0：先修顺手程度 | 对齐、间距、操作层级、图标、复制反馈、行菜单、名称规则、字段错误、详情重试、保存后定位 | 主要为 SwiftUI 与 AppModel 调整；保留数据格式和 Go 规则 |
| P1：完善日常使用 | 详情源文切换、编辑预览、正确显示常用 Markdown 列表/引用、创建副本、历史查看与恢复、从剪贴板新建 | 历史复用已有 Core；副本复用创建接口并处理重名；剪贴板文本先进入草稿，确认保存后落库 |
| P1：改善大量资料查找 | 明确搜索范围，增加可选的正文全文搜索与匹配摘要 | 当前只有名称/描述/标签搜索；正文搜索应由 Go 提供查询，用内容 hash 失效缓存，不让 Swift 绕开 Core 直接读取资料库 |
| P2：按实际需求决定 | 收藏、最近使用、排序偏好、批量标签/导出、更完整 Markdown 支持 | 收藏/使用时间需先确定本机偏好还是跨设备数据；当前 DTO 没有修改时间，不能凭空增加「最近修改」排序 |
| 可选的独立阶段 | 变量定义、填写变量、渲染后复制 | 当前产品文档明确不提供填写变量入口；除非本次确认调整方向，否则继续兼容保存已有变量，不自动恢复整套变量 UI |

不建议首批加入 AI 生成 Prompt、模型调用、在线模板市场或 Agent 自动投递。这些会扩大产品边界，不能解决当前的对齐和复用效率问题。

## 4. 实施顺序与代码范围

1. 先确定阅读优先或紧凑浏览，以及编辑器的基本结构；使用同一组示例内容评审浅色、深色和窄窗。
2. 落地 P0。尺寸集中到 `SKMDesign`；Prompts 使用独立的布局修饰器，先不直接改变所有 Skills/Projects 共用的阅读边距。
3. 将目前集中在 `PromptsViews.swift` 的列表、详情、编辑器和草稿状态按职责拆开，便于单独验证。只在改到相应功能时拆分，不进行全仓重构。
4. 落地 P1 的副本、预览、历史入口和剪贴板新建。复用 Go 现有能力，Swift 负责展示、选择和草稿。
5. 再决定全文搜索及 P2。涉及新 Core 方法时同步声明能力，并覆盖旧数据和多端修改；不为纯布局调整升级存储 schema。

## 5. 验收标准

- **视觉**：980 × 640、1280 × 800、1440 × 900 三档主窗口检查；浅色/深色、中英文、长名称、多标签及多段正文均不遮挡、不溢出。相同语义层级共用对齐线；列表区域和详情区域不要求机械地共用同一个屏幕坐标。
- **阅读**：标题、列表、引用、代码块保持清晰层级；预览与源文切换不丢选择、不改数据。长正文不因复制按钮永久预留大块右边空白。
- **复制**：从列表和详情复制得到完全一致的 Markdown 正文；选中文本时 `⌘C` 继续只复制选区。全文快捷键需放到明确菜单项，避免覆盖系统文字复制。
- **编辑**：创建后定位；已有名称不能误改；错误就地说明；`⌘S` 保存；取消时可继续编辑；并发冲突不丢草稿；未编辑的变量定义保持原样。
- **副本与历史**：连续创建副本不覆盖原条目；恢复历史前展示差异并确认；恢复后更新详情，原来的当前版本仍可从历史找回。
- **性能**：大量条目不因选择、滚动或搜索触发逐行 Core 请求；长正文预览避免在每次视图更新中重复解析。用实际资料量测量，不先编造固定延迟承诺。
- **回归**：现有 Go 测试、macOS 单元测试和相关 XCUITest；补充名称不可变、创建后选择、复制正文、详情失败重试及中英文窄窗布局的行为验证。共享组件修改额外检查 Skills/Projects。

## 6. 评审建议

建议先批准 P0 和 P1 中「预览、创建副本、历史入口」这一批；保持标签分组和变量入口现状。这样第一轮就能明显改善视觉秩序和高频操作，不需要先迁移数据或扩大产品边界。

本次已确认以查找、阅读、复制和编辑为重点。变量定义继续兼容，变量工作流不进入首批；后续需要时再单独评审。

对齐、间距和操作组织参考 Apple 官方 [Layout](https://developer.apple.com/design/human-interface-guidelines/layout)、[Toolbars](https://developer.apple.com/design/human-interface-guidelines/toolbars) 与 [Buttons](https://developer.apple.com/design/human-interface-guidelines/buttons) 指南。具体尺寸、信息层级与阶段划分是针对本项目的设计建议。
