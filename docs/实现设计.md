# skm 实现设计

> 当前实现版本：0.2，持久化 schema：v2。

## 1. 产品边界

skm 是本地 Skill Library 和部署管理器。它不执行 Skill 中的脚本，不管理 Agent
账号，不替代 Git 凭证系统，也不依靠 Agent 自身不一致的同名覆盖规则。

核心目标：

1. 用户拥有一个独立于 Agent 的个人 Skill Library。
2. Library Skill 可以按 Agent 启用和禁用。
3. 标签属于个人 Library，可用于组合筛选和批量启用。
4. 项目可以引用可恢复依赖，或维护独立副本。
5. 所有部署变更经过可检查、幂等的 Plan。

详细产品语义见 [Library、Activation 与 Project 设计](技能库激活与项目设计.md)。

## 2. 领域模型

| 对象 | 职责 |
| --- | --- |
| `Skill` | Library 或项目 Skill 的 ID、标签、hash、路径和来源 |
| `Source` | Git URL、ref、绑定路径和当前 revision |
| `Activation` | Skill、Agent、部署位置和期望模式 |
| `ProjectDependency` | 可恢复 Git 依赖及锁定 revision/hash |
| `Project` | 本机登记的项目 ID 和规范化路径 |
| `Deployment` | skm 已创建的实际目标及所有权证据 |
| `Plan` | 幂等文件操作及输入摘要 |

核心枚举：

```text
Skill.location       library | project
Activation.placement user | project
LinkMode              auto | symlink | copy
Agent                 claude | codex
```

`location` 表示内容由谁持有，`placement` 表示部署到哪里。二者不能共用同一个
Scope 类型。

## 3. 本地布局

用户数据：

```text
~/.skm/
├── config.yaml
├── catalog.yaml
├── projects.yaml
├── sources.yaml
├── objects/<hash>/<name>/
├── sources/<source>/
├── state/state.yaml
└── locks/state.lock
```

项目数据：

```text
<project>/.skm/
├── project.yaml
├── lock.yaml
└── skills/<name>/          # 仅 vendored Skill
```

Agent 目标：

```text
User:
  ~/.claude/skills/<name>
  ~/.codex/skills/<name>

Project:
  <project>/.claude/skills/<name>
  <project>/.codex/skills/<name>
```

Agent 目标是生成状态。Require/vendor 模式下，`.skm/project.yaml`、`.skm/lock.yaml`
和 `.skm/skills/` 是可提交的项目状态；本机即时部署模式的状态保存在用户侧，项目目录
只保留最终 Agent 软链或复制结果。

## 4. Library 导入

本地导入流程：

```text
validate -> hash -> immutable object -> catalog upsert
```

Git 更新流程：

```text
clone -> checkout ref -> discover -> validate -> snapshot -> catalog upsert
```

Git Source 更新不会直接修改已部署目录；Planner 根据 Activation 将用户链接原子
切换到新快照。项目 require 使用锁定快照，不随个人 Source 更新自动漂移。

Library `remove` 删除索引后，对当前快照执行可达性检查：剩余 Library 条目、固定
Activation、Deployment 和当前项目依赖均视为引用。无引用快照立即删除；历史版本
等孤立对象由 `prune` 统一清理。清理只接受标准 hash/name 布局，不跟随异常符号链接。

## 5. Activation 与 Planner

个人 `enable` 只创建用户 Placement Activation。项目 Activation 可以由项目
`project.yaml` 派生，也可以由用户侧注册项目的即时部署命令创建。

Planner 状态：

| 状态 | 含义 |
| --- | --- |
| `create` | 目标不存在 |
| `unchanged` | 当前部署正确 |
| `replace-managed` | skm 管理的目标需要更新 |
| `conflict-unmanaged` | 目标未知或被外部修改 |
| `broken` | 已记录目标丢失 |

相同 Agent/Placement 中两个 Skill 指向同名目标时直接失败，不根据来源或层级暗中
覆盖。Apply 使用临时路径和原子替换。

### 5.1 本机项目部署

`project add` 只将项目路径登记到用户侧 `~/.skm/projects.yaml`，不向项目写入 `.skm`
文件。`project link` 和 `project copy` 使用同一套 project Placement Activation 和
Planner，目标分别为：

```text
<project>/.claude/skills/<name>
<project>/.codex/skills/<name>
```

本机项目模式是即时部署模型：项目目录中的 Agent 内容是最终运行结果，项目运行时不需要
skm。软链模式仍依赖 `~/.skm/objects` 中的快照；复制模式将内容复制到项目 Agent 目录，
可以在不安装 skm 的情况下运行。两种模式都记录 hash，重复操作保持幂等，目标冲突时
拒绝覆盖。

项目注册表是本机索引，不是团队可恢复配置。需要跨机器恢复时仍使用 `project require`
或 `project vendor`；需要让复制结果直接可用时，应由项目自己的 Git 工作流提交复制的
Agent Skill 目录。

## 6. 项目 require

Require 记录：

- 完整 Skill ID 和名称；
- Source 名、Git URL、ref 和仓库内路径；
- 精确 revision 和内容 hash；
- 标签、Agent 和部署模式。

`project apply` 优先复用本机已有的锁定对象，否则按 Git URL 和 revision 获取快照。
获取项目锁定快照不会改变用户 Source 绑定或当前 Library 版本。

用户 Activation 只有在同一 Agent 上提供完全相同的 ID 和 hash 时，才能满足项目
依赖。任何同名不同 ID/版本都报告冲突。

## 7. 项目 vendor

Vendor 将 Library 快照复制到 `.skm/skills/<name>`，生成新的 `project/<name>` ID，
并记录 `forkedFrom` 和 `forkedRevision`。Library 原版不受影响。

`project apply` 每次重新验证 vendored 内容并刷新 hash，因此团队可以直接在仓库中
修改项目版本。项目与个人版本之间没有隐式同步。

## 8. 标签

标签只由个人 Library 管理：

- 导入时规范化；
- 未指定时使用 `defaults.tags`；
- 多标签查询为 AND；
- Source 更新保留用户已修改标签；
- `enable --tag` 批量创建 Activation。

Vendored Skill 在复制时继承 Library 标签，也可以通过 `project vendor --tag` 指定
项目副本标签；之后不受个人标签重命名影响。

## 9. 安全边界

- 拒绝包含内嵌凭证的 Git URL。
- 限制 Skill 文件数、单文件大小和总大小。
- 阻止逃逸 Skill 根目录的软链接。
- 不覆盖未由 skm 管理的 Agent 目标。
- 删除前验证目标、Placement 和项目根目录。
- 项目 require 拒绝本地-only Source，避免生成无法供团队恢复的 Manifest。
- 全局文件锁避免 CLI 并发修改状态。

## 10. schema v1 迁移

读取旧数据时：

```text
Catalog global/personal -> library
Catalog project         -> project
Installation global/personal -> user Activation
Installation project         -> project Activation
```

下一次写入时保存为 schema v2，并移除旧 `scope` 与 `installations` 字段。

## 11. 后续方向

- `project diff-vendor` 和显式 `promote` 工作流。
- 跨已知项目的依赖反向索引，增强 Library 删除检查。
- 项目恢复的离线包或镜像 Source。
- macOS App 使用稳定 JSON envelope 调用同一 CLI 领域逻辑。
