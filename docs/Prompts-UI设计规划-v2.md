# Prompts UI 设计规划 v2

日期：2026-10-28。更新：2026-10-29，已按方案 A 完成第一版实现；验证结果与实际边界见 [实现记录](Prompts-UI实现记录.md)。下文保留设计时的判断和分阶段计划，验收清单不代表所有项目已测完。

本轮读取了当前 SwiftUI / Go 实现，并查看正在运行的 SKM 的 Prompts 列表、详情和编辑弹窗。仅展开列表、打开并取消编辑，没有更改 Prompt 数据。现有《macOS-Prompts改进方案》保留；本稿重点补充信息架构、分类和视觉执行，并建议替换其中“继续把全部与标签并列展开”的方案。

## 1. 设计判断

建议做成一个安静、精确、阅读优先的原生文本资料库。左侧回答“看哪一类”，中间回答“选哪一条”，右侧回答“内容是什么、怎样使用”。

当前问题并不只是颜色或圆角：

| 已确认的问题 | 直接影响 | 对应改动 |
| --- | --- | --- |
| 中栏先展示“全部”，再展示标签分组；每组重复渲染相同条目 | 实际有 17 条时，标签入口被推到列表底部；多标签还会重复出现 | 分类与条目列表分离；当前结果按 ID 去重 |
| 所有组可全部收起，而详情继续显示之前选择 | 中栏接近空白，详情缺少可见的所属条目 | 取消列表的“全部”折叠；筛选变化时校正选择 |
| 标题、搜索框、行、详情、正文分别定义 inset | 同一内容区没有稳定的左边线，文字像在逐层后退 | 每栏建立独立的统一对齐轴，删除补偿型 padding |
| 顶部复制用回形针、导出用气泡、编辑用标签；五个操作同等强调 | 需要猜按钮意义，操作缺乏主次 | 复制正文、编辑、更多；改用语义正确的 SF Symbols |
| 来源绿徽章、橙色标签、绿色健康勾、正文卡片同时出现 | 辅助信息比正文更抢眼 | 来源降为文字，标签中性色，去掉无独立检查语义的健康勾 |
| 正文外层卡片占用额外左右空间，还重复提供复制入口 | 短文像表单，长文被挤窄 | 正文直接排版，只给代码块、引用等语义块容器 |
| 编辑弹窗顶部大图标和宣传式副标题占空间；标签容器固定高度 | 编辑密度低，少量标签下方形成空洞 | 紧凑标题栏、自然高度的已选标签、按需打开标签选择 |
| 编辑时名称可输入，而 Go 禁止改名 | UI 许诺了实际不支持的行为 | 编辑时显示只读名称；新建时完整说明命名规则 |

主要代码依据：`PromptsViews.swift` 的分组 List、工具栏和编辑器；`PromptSummaryRow.swift`；`RootView.swift` 的三栏宽度；`DesignSystem.swift` 的阅读 inset；`TagGroupHeader.swift` 的标签选择器；`AppModel.savePrompt`；`internal/application/prompts.go` 的不可变名称规则。

## 2. 推荐信息架构

### 方案 A：侧栏分类，推荐

保留三栏，把当前 Prompts 的分类导航放入左栏的独立区域：

```text
左栏 200–220              中栏 300–340                 详情 自适应
┌────────────────────┬────────────────────────┬────────────────────────────┐
│ Skills             │ 全部 Prompt       ＋ ⋯ │          编辑  复制正文  ⋯ │
│ Prompts            ├────────────────────────┼────────────────────────────┤
│ Projects           │ 搜索名称、描述、标签   │                            │
│                    │                        │ code-review                │
│ PROMPT 分类        │ code-review            │ 审查代码并给出可执行建议   │
│ 全部 Prompt     17 │ 审查代码并给出建议     │ 本地 · 开发 · 审查          │
│ 未分类           0 │                        │                            │
│                    │ api-design             │ 预览 / 源文                │
│ 标签               │ 整理接口契约与边界     │ ────────────────────────── │
│ 简小知          16 │                        │ 你是一名资深工程师。       │
│ general          1 │ …                      │                            │
│ 管理标签…          │                        │ 审查重点                   │
│                    │                        │ • 正确性与边界             │
│ 设置 / 同步        │ 共 17 项               │ • 命名与可维护性           │
└────────────────────┴────────────────────────┴────────────────────────────┘
```

此图的分类计数来自本次观察，条目内容仅为示例。分类区域仅在 Prompts 模块出现；全局导航仍然保持 Skills / Prompts / Projects 的顺序。

- 全局 Prompts 使用轻量的当前模块标记；具体筛选使用选中背景，避免两个同权重选中块争夺视线。
- 分类区位于全局导航下方，用 20–24 pt 空隙和简洁标题区分。不要在一个全局导航条目里嵌入多层树。
- 标签有自己的可滚动区域；头部、全局导航和底部设置位置稳定。大量标签时提供“查找标签”弹出选择器，不强行铺开几十个彩色胶囊。
- 列表标题显示当前筛选，如“全部 Prompt”“简小知”“未分类”；分类名过长尾部截断，悬停与辅助功能可读完整名称。

优点：分类始终可见，列表连续且不重复；利用现有左栏留白，适合后续资料增长。代价：需要调整 `RootView` 的侧栏区域和跨视图筛选状态；须回归 Skills / Projects 导航。

### 方案 B：列表顶部分类，备选

左栏保持现状，在中栏标题与搜索区域之间提供“全部 Prompt ▾”，打开后选择未分类或标签。其余列表、详情和编辑器与 A 一致。

优点：改动集中在 Prompts，保留当前全局导航结构。代价：标签被收进菜单，切换分类多一步；资料多时可见性弱于 A。

建议选择 A 作为最终方向。A / B 是评审备选，不作为产品中新增的两种布局设置。

## 3. 分类的完整规则

第一阶段使用已有 tags，不新增与标签重叠的“文件夹 / 项目 / 场景”三套数据，也不自动改动用户现有标签。

| 概念 | 规则 |
| --- | --- |
| 全部 Prompt | 所有条目按唯一 ID 展示一次，不是可收起的组 |
| 未分类 | `tags` 为空；`general` 仍是实际标签，不等同未分类 |
| 标签 | 多对多；一个 Prompt 可以属于多个标签，但单个结果列表不重复 |
| 标签点击 | 第一阶段单选，便于理解；切换标签保留搜索词，两者取交集 |
| 数量 | 侧栏显示该类总量，搜索不让分类计数跳动；底部显示“找到 N 项 · 当前类共 M 项” |
| 搜索 | 第一阶段明确只查名称、描述、标签；不声称是正文全文搜索 |
| 排序 | 默认名称自然升序；名称升序/降序可选，不提供当前数据无法支持的最近修改排序 |
| 新建 | 在标签视图中新建时预选该标签；在全部/未分类中新建时草稿 tags 为空。Core 创建时保持空标签，直接进入未分类；编辑时清空标签同样进入未分类 |
| 无结果 | 保留筛选上下文，展示清除搜索或查看全部入口；不偷偷清空搜索 |
| 选择 | 旧条目仍在结果中则保留；否则选择第一条；无结果则清空详情 |
| 创建/导入完成 | 选择并定位新条目；若被筛选挡住，切到全部并清除搜索，显示“已显示新建条目”的一次性提示 |
| 标签管理 | 复用现有创建、重命名、合并、移除能力；移除说明“仅解除标签，不删除 Prompt” |
| 空标签 | 用户手动创建的零条目标签仍可显示；自动生成的“未分类”即使为零也保留稳定位置 |

项目名称标签与用途标签可以同时存在。例如 `简小知 + 代码审查`；这只是组织建议，不自动批量打标。若未来确实需要“一个主分类 + 多个标签”，应作为独立数据设计评审，明确迁移与冲突规则。

## 4. 视觉执行规格

以下是本项目首轮设计基线，需经原生窗口实测微调，不是 Apple 强制尺寸。

| 项目 | 建议规格与约束 |
| --- | --- |
| 空间节奏 | 4 / 8 / 12 / 16 / 20 / 24 / 32 pt；同语义位置统一 token |
| 顶栏 | 中栏、详情栏统一 52 pt 基线；光学居中图标，不使用不必要的外框 |
| 侧栏 | 默认约 208 pt；计数等宽数字并右对齐；图标独占固定槽 |
| 中栏 | 默认约 320 pt，允许 280–360；标题、搜索框外缘、行文字共同 20 pt 起点 |
| 列表行 | 名称 14 pt semibold；描述 12–13 pt secondary，最多两行；常规约 76–84 pt，较大文字允许增长 |
| 列表标签 | 默认不在每条摘要重复显示同一标签；标签在筛选与详情中完整表达，减少当前整列重复标签行 |
| 列表选中 | 轻量系统强调底色 + 清晰文字；与 hover 区分；失焦后仍可判断选择，不只靠颜色 |
| 分隔线 | 列表按文字起点缩进的弱分隔；选中背景不叠加重边框和阴影 |
| 详情边距 | 左右对称 32 pt；窄窗降为 24 pt；标题、描述、元数据、模式切换和正文同轴 |
| 阅读宽度 | 正文最大约 800 pt，靠左；大窗多余空间留在右侧，不让每段文字横跨整个屏幕 |
| 详情文字 | 标题 26–28 pt semibold；描述 14 pt；正文 14–15 pt；辅助信息 12–13 pt |
| 标题处理 | 长名称允许换行；路径/代码可局部等宽；不把普通阅读正文全部设为等宽 |
| 颜色 | 系统表面与文本色；沿用 App 强调色。标签中性，错误才用红；取消橙、紫、绿同时做装饰 |
| 圆角与阴影 | 输入/轻量选中约 6–8 pt；大容器依原生窗口；正文无整块卡片；阴影只服务弹出层 |
| 图标 | 复制 `doc.on.doc`；编辑 `square.and.pencil`；导入 `square.and.arrow.down`；导出 `square.and.arrow.up`；更多 `ellipsis` |

浅色/深色必须各自检查；颜色使用语义或动态值。支持系统强调色、提高对比度、降低动态效果；辅助信息不能靠过低透明度换取“干净”。

## 5. 详情页

阅读区顺序固定为：名称 → 描述 → 轻量元数据 → 预览/源文 → 正文。

- 复制正文为主要操作，带明确文字；编辑为次操作；更多承载导出、快速查看、删除。副本与历史可以后续接入，不用灰按钮占位。
- 复制只复制保存的 Markdown 正文，保持空格、换行和占位符，与当前预览/源文模式无关。按钮短暂显示“已复制”，只保留这一处视觉反馈，辅助功能仍可播报。
- 选中文本的 `⌘C` 保持系统行为；若添加“复制全文”快捷键，使用独立菜单命令并避开冲突。
- 移除重复的“内容”标题、大卡片与顶部绿色健康勾。来源显示为“本地”等次级文本；标签可点击筛选，零标签显示轻量“未分类”。
- Markdown 首批覆盖段落、标题、列表、引用和代码块；源文等宽，代码块可以局部横向滚动，正文区域不横向滚动。
- 加载中、无选择、无结果、读取失败分别设计。失败展示重试；快速切换条目时，旧请求不能覆盖新条目。

## 6. 新建 / 编辑器

保留“属性在左、正文在右”的结构，减少装饰，将空间用于内容。

- 顶栏用紧凑“新建 Prompt / 编辑 Prompt”和必要状态，去掉 48 pt 渐变图标和重复说明。
- 默认约 880 × 600，左侧属性区约 240–260 pt；最终按宿主可用空间决定大小，避免固定 920 × 640 在最小主窗内显得拥挤。窄时属性折到上方，正文仍保有可编辑面积。
- 新建名称明确为 1–64 位小写字母、数字、连字符，以字母或数字开头/结尾；编辑名称只读并注明创建后固定。新建时检查重名，最终仍由 Core 校验。
- 描述、正文保留既有必填约束；无变化时禁用保存。字段失焦或尝试保存后展示具体错误，避免刚打开就满屏红字。
- 标签区优先显示已选标签，自然换行；“添加标签”打开可搜索、多选的选择器，支持直接创建。用新的 Prompt 专用组件起步，避免误改 Skill 弹窗。
- 新建标签先进入草稿，保存成功后再提交相关偏好；取消编辑不应遗留本次临时创建的标签。既有变量定义完整保留。
- 正文标题和输入文本首字符对齐，核对 `TextEditor` 原生 inset；不要继续用另一层 padding 凑齐。
- “编辑 / 预览”切换保留光标和滚动状态；新建先聚焦名称，编辑先聚焦正文。
- 底部固定草稿状态、取消、保存；支持 `⌘S`。取消有改动草稿继续确认；失败保留输入。
- 并发冲突在弹窗中清楚展示草稿与磁盘版本，保留现有处理能力；不可借视觉简化去掉冲突保护。

## 7. 实施拆分与代码边界

### 第一批：完整的视觉与信息架构改版

1. **分类与唯一列表**：添加 `PromptBrowserState` 或等价视图状态，统一拥有 query/filter/sort/selection；用派生结果处理计数、筛选和选择修正。A 方案添加 `PromptFilterSidebar`，接入 `RootView`。
2. **列表与工具栏**：重做 `PromptsListView`、`PromptSummaryRow`；统一边距、摘要密度、状态；行右键菜单操作当前行，而非错误地操作别的已选条目。
3. **详情阅读区**：拆出 `PromptDetailView`，引入 Prompt 专用阅读布局、元数据与操作区；正确图标、复制反馈、失败重试。
4. **编辑器**：拆出 `PromptEditorSheet`、草稿模型与标签选择器；紧凑布局、名称只读、错误提示、无改动禁用保存。
5. **保存定位**：`AppModel.savePrompt/importPrompt` 使用 Core 返回的 ID，在刷新完成后定位；处理过滤条件与新增条目的冲突。
6. **预览/源文**：共用渲染逻辑，补常见 Markdown 列表/引用。若改共享 `MarkdownBodyView`，单独回归 Skills 的显示。

这批形成可独立验收的闭环：分类 → 搜索 → 选择 → 阅读 → 复制 → 编辑 → 返回定位。

### 第二批：完成高频管理动作

- 创建副本：复用创建 API；处理名称长度与连续重名；保留标签和变量。
- 历史查看与恢复：复用 Core；独立设计对比、恢复确认和恢复后的选择，不和纯布局修改捆绑。
- 标签管理弹窗：对齐主界面的文字、按钮、空态；保留现有重命名/合并与解绑规则。

### 后续独立评审

收藏、最近使用、最近修改、批量处理、正文全文搜索、变量填写。前几个需要明确状态归属/数据支持；全文搜索应由 Go/Core 提供，不让 Swift 绕过核心存储规则。当前变量定义兼容保留，变量填写入口不在这次范围。

## 8. 验收清单

- 窗口：980 × 640、1280 × 800、1440 × 900；浅/深色、中文/英文、放大文字。
- 数据：0、1、17、数百条；零标签、多标签、超长标签、已创建但未使用的标签。
- 内容：长英文名称、中文两行描述、长正文、标题/列表/引用/代码块、极长代码行。
- 视觉：同栏对齐轴一致；两栏顶栏同高；中栏不因展开组变空；详情没有层层缩进；编辑器标签少时不留固定空洞。
- 交互：切换标签不重复条目，搜索与分类取交集；无结果不显示旧详情；删除/重命名当前标签后筛选状态有效。
- 编辑：只读名称、字段校验、无修改禁用、保存后定位、取消无残留、自定义标签取消不落地、并发不丢草稿。
- 复制：列表与详情得到相同原始正文；局部选择的系统复制保持正常。
- 辅助功能：键盘能完成筛选、选行、编辑、保存；按钮可读名称；选中、失败、复制反馈不只靠颜色。
- 性能：标签计数和摘要基于已加载 summaries，不逐行请求 Core；解析 Markdown 不随无关视图更新反复执行。
- 验证：实施后运行 `macos/README.md` 的构建/单元/UI 测试，使用隔离测试根；按仓库规范运行 Go 测试和构建。规划本身未执行构建，不宣称上述验收已通过。

## 9. 评审结论建议
