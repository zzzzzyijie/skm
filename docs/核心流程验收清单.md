## 发布前阻塞与闭环项

### 1. Web API 写操作缺少跨站请求防护

`internal/server/server.go` 当前主要设置响应安全头，但写接口没有统一校验请求的
`Origin`、`Host`、`Content-Type` 或 CSRF token。本地服务包含多个会修改 Library、Source、
Activation 和 Project 状态的 POST/DELETE 接口，因此发布前应增加统一中间件，并为允许和拒绝
场景补测试。

验收标准：

- 仅接受预期的本机 Origin/Host；无 Origin 的 CLI 或受信任调用规则必须明确。
- 写接口仅接受规定的 JSON Content-Type，或使用不可被简单跨站表单构造的 CSRF 方案。
- 所有状态变更路由共用同一套防护，并覆盖正向、跨站和异常请求测试。

### 2. macOS 正式发布闭环

macOS 原生 App 当前工程版本为 `0.5.3 (Build 3)`，远端最新 Tag 为 `v0.5.0`；真实签名与
公证验收曾使用 `0.6.0 (Build 3)` 发布参数，但没有创建对应 Tag 或 Release。正式发布前需要先
统一版本号，不能直接把本地验收参数视为已发布版本。

尚需完成：

- 生成独立的 Sparkle EdDSA 公私钥；公钥注入 App，私钥只保存于安全位置或 GitHub Secret。
- 在 GitHub Actions 配置 Developer ID `.p12`、App Store Connect API Key 和 Sparkle 密钥对应的 Secrets。
- 触发正式 Tag 工作流，验证签名、公证票据、stapling、Gatekeeper、Formula、Cask、appcast 和 Release 产物。
- 在无 Go、Homebrew 和 SKM CLI 的 Intel 与 Apple Silicon Mac 上人工验证 DMG 安装、启动、Core 握手和主要读写流程。
- 使用 Accessibility Inspector 完成 VoiceOver 焦点顺序、Full Keyboard Access、字体缩放、高对比度、减少动态效果、浅色/深色和窄窗口验收。

验收标准：

- Tag、App、Core、DMG、ZIP、Formula、Cask 与 appcast 使用同一正式版本。
- GitHub Release 工作流在两种架构 runner 上全部通过，产物可从全新环境安装并启动。
- Sparkle 可以校验签名 appcast 和更新包；仓库及产物中不包含任何私钥、证书密码或公证凭据。
- 人工可访问性与不同窗口、外观设置验收有结果记录。

### 3. Web 更新 Git Source 后未同步已部署 Skill（已解决）

侧边栏品牌右侧和移动端品牌区现已提供统一同步入口；未配置来源时直接打开设置中的 Git 同步页。
`/api/sync` 会按来源独立更新，保留每个来源的成功或失败结果，并在至少一个来源成功后通过 Planner
刷新所有托管部署。一个来源失败不会阻止其他来源落库和部署，部署冲突会作为独立错误返回。

已覆盖：

- 设置页添加、校验、列出和删除 Git 来源，凭据继续由 SSH Agent 或 Git Credential Helper 管理。
- 来源仓库先完整 clone、发现和校验，再替换 checkout，并一次性原子写入 catalog 索引。
- 自动化测试验证来源失败隔离、用户级 activation 刷新、删除绑定保留 Library 快照，以及失败更新不改变 catalog、binding 和 checkout。

### 4. 空白项目首次部署（已解决）

空白项目现在会回退到已配置 Agent，再回退到受支持的 Codex Agent；Web 与 macOS 原生界面均可
先选择 Agent、预览部署，再由 Core 创建 `.<agent>/skills` 目标目录。

已覆盖：

- 空白项目首次 Link/Copy 部署与目标目录创建。
- 未知目标冲突阻断、取消部署、解绑和重复扫描。
- 原生 XCUITest 覆盖项目登记与 Workspace 预览入口。
